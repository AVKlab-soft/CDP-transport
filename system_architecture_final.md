# Архитектура системы автоматизации "Виртуальная корпорация"

## 1. Общая концепция
Система представляет собой двухконтурную архитектуру, где **Бизнес-логика** (агенты и процессы) отделена от **Технической реализации** (движок исполнения). 
- **Принцип работы:** Всё происходит в оперативной памяти. Запись на диск (Obsidian) — только финального результата или явных контрольных точек.
- **Ограничения:** Windows 10 x86, 500 МБ ОЗУ, без установки стороннего ПО (кроме браузера ungoogled-chromium).
- **Ядро:** PowerShell + .NET (Named Pipes / WebSocket).

---

## 2. Контур 1: Бизнес-логика ("Виртуальная корпорация")
Этот уровень существует в виде файлов Markdown в базе знаний Obsidian. Он определяет **ЧТО** делать, но не **КАК**.

### 2.1. Агенты (Сотрудники)
- **Сущность:** Не являются исполняемым кодом. Это файлы `.md` с системными промптами.
- **Хранение:** Папка `Agents/`. Пример: `Agents/Copywriter.md`, `Agents/Analyst.md`.
- **Содержимое:** Текст инструкции (System Prompt), роль, стиль ответа.

### 2.2. Бизнес-процессы (Графы работ)
- **Сущность:** Маршруты движения данных между агентами. Аналог LangGraph, реализованный скриптово.
- **Хранение:** Папка `Processes/`. Пример: `Processes/New_Idea_Process.json` или `.md`.
- **Логика:** Последовательность шагов.
  ```text
  Шаг 1: Взять файл -> Агент "Идентификатор" -> Получить тег "Маркетинг".
  Шаг 2: Если тег "Маркетинг" -> Передать Агенту "Копирайтер".
  Шаг 3: Результат Копирайтера -> Записать в файл.
  ```
- **Исполнение:** Оркестратор читает этот граф и последовательно меняет содержимое контейнера.

---

## 3. Контур 2: Техническая логика ("Мета-движок")
Единый долгоживущий процесс (Service), управляющий потоком данных в памяти.

### 3.1. Объект "Контейнер" (Task Container)
Единица передачи данных внутри системы. Существует только в RAM.
```powershell
$Container = @{
    Id          = [Guid]::NewGuid()
    SourceFile  = "input.md"       # Имя исходника (для лога)
    Content     = "..."            # ТЕКУЩЕЕ состояние текста (String)
    Prompt      = "..."            # Текущий системный промпт (из файла агента)
    TargetModel = "Qwen"           # Маркировка провайдера (DeepSeek, Qwen, Kimi, GPT)
    Context     = @{}              # Доп. метаданные (теги, история шагов)
    Status      = "Processing"     # Статус выполнения
}
```

### 3.2. Модули движка

#### А. Оркестратор (Orchestrator)
- **Роль:** Главный мозг системы.
- **Функции:**
  1. Слушает триггеры (появление файлов во `Input`).
  2. Инициализирует **Контейнер**, загружая текст файла в переменную `$Container.Content`.
  3. Читает файл **Бизнес-процесса**.
  4. Циклично выполняет шаги графа:
     - Берет шаг из графа.
     - Находит соответствующего **Агента** (загружает промпт из `.md`).
     - Обновляет `$Container.Prompt` и `$Container.TargetModel`.
     - Отправляет контейнер в **CDP Модуль**.
     - Получает ответ, обновляет `$Container.Content`.
     - Переходит к следующему шагу графа.
  5. Если граф завершен — вызывает запись на диск.

#### Б. CDP Модуль (Транспорт)
- **Роль:** "Тупой" исполнитель. Не принимает решений, не знает про агентов.
- **Вход:** Контейнер (текст + промпт + модель).
- **Логика:** Жестко зашитые сценарии для каждого провайдера.
  - *Если Model == Qwen:* Открыть вкладку Qwen -> Вставить промпт + контент -> Кликнуть "Отправить" -> Ждать ответа -> Скопировать текст.
  - *Если Model == DeepSeek:* Открыть вкладку DeepSeek -> ... (свой сценарий селекторов).
- **Выход:** Обновленный Контейнер (поле `Content` заменено на ответ ИИ).
- **Особенность:** Вся логика селекторов, кликов и ожиданий находится внутри модуля. Внешняя система просто говорит "Отправь это в Qwen".

#### В. Менеджер памяти (Memory Manager)
- Обеспечивает хранение активных контейнеров в RAM.
- Гарантирует, что промежуточные результаты не пишутся на диск.
- Очищает память после завершения задачи.

## 4. Поток данных (Data Flow)

1. **Старт:** Пользователь создает `idea.md` в папке `Input`.
2. **Захват:** Оркестратор считывает файл в переменную, удаляет оригинал (или перемещает в `Processing`).
3. **Инициализация:** Создается объект `$Container` в памяти.
4. **Цикл обработки (согласно Бизнес-процессу):**
   - **Шаг 1:** Оркестратор загружает промпт "Идентификатора". Устанавливает `TargetModel = Qwen`.
   - **Действие:** Отправляет `$Container` в CDP Модуль.
   - **CDP:** Подключается к браузеру, выполняет скрипт для Qwen, получает ответ "Это маркетинговая задача".
   - **Возврат:** CDP возвращает `$Container` с новым текстом.
   - **Логика:** Оркестратор анализирует ответ, понимает, что следующий шаг — "Копирайтер".
   - **Шаг 2:** Оркестратор загружает промпт "Копирайтера", формирует новый запрос на основе предыдущего ответа.
   - **Действие:** Снова отправляет в CDP (возможно, на другую модель).
   - **Финал шага:** Получен готовый текст статьи.
5. **Запись:** Оркестратор видит конец графа. Записывает `$Container.Content` в файл `Output/result_idea.md` в Obsidian.
6. **Очистка:** Контейнер уничтожается, память освобождается.

## 5. Технические требования и решения

| Компонент | Решение | Обоснование |
| :--- | :--- | :--- |
| **Язык** | PowerShell 5.1 | Встроен в Windows 10, доступ к .NET классам. |
| **Межпроцессное взаимодействие** | Named Pipes (RAM) | Если модули вынесены в отдельные процессы для надежности. Передача без диска. |
| **Внутрипроцессное** | Переменные PowerShell | Максимальная скорость, 0 накладных расходов. |
| **Браузер** | ungoogled-chromium (x86) | Запуск с флагом `--remote-debugging-port=9222`. Профиль с авторизацией. |
| **Протокол CDP** | WebSocket (.NET ClientWebSocket) | Прямое управление браузером без Selenium. |
| **Хранение состояния** | RAM (Hash Tables) | Соответствует требованию "не писать промежуточные файлы". |
| **Конфигурация** | JSON / MD файлы | Легкое редактирование агентов и процессов пользователем. |

## 6. План разработки

1. **Прототип CDP Core:** Реализация подключения к браузеру и базовых действий (клик, ввод, чтение) для одного провайдера (Qwen).
2. **Система Контейнеров:** Реализация структуры данных в памяти и передача её между функциями.
3. **Оркестратор (MVP):** Чтение простого линейного бизнес-процесса (1 шаг) и запуск CDP.
4. **Расширение CDP:** Добавление поддержки других провайдеров (DeepSeek, Kimi) через переключатели логики.
5. **Графовая логика:** Реализация ветвлений в Оркестраторе (если ответ Х -> шаг А, иначе шаг Б).
6. **Интеграция с Obsidian:** Автоматическая запись финальных результатов в нужные папки.

---

## 7. Границы ответственности

- **Агенты (файлы):** Знают только свою роль (текст промпта). Не знают о существовании других агентов или кода.
- **Бизнес-процессы (файлы):** Знают только порядок шагов. Не умеют выполнять действия.
- **Оркестратор:** Знает порядок шагов, умеет грузить промпты, управлять контейнером. Не умеет работать с браузером напрямую.
- **CDP Модуль:** Умеет только нажимать кнопки и читать текст в браузере. Не знает, что такое "агент" или "бизнес-процесс".

Эта модульность позволяет менять промпты, добавлять новые процессы или править логику кликов в браузере независимо друг от друга.
