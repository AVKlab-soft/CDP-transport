# История запросов пользователя

## 1. Начальный вопрос о формате работы
**Запрос:**
"Как с тобой работать? Тебе сразу готовые ТЗ и планы, чтобы прогать, Или ты можешь помогать сперва спроектировать и только после приступать?"

**Контекст:**
Пользователь уточняет возможности взаимодействия: работа с готовым ТЗ или совместное проектирование с нуля.

---

## 2. Первичное описание идеи системы
**Запрос:**
"Пока идея. автоматическая обработка файлов, по типу электронного документооборота в офисе.
Будет папка, в которой будут размещаться файлы. Я настрою алгоритм по триггерам, который будет брать с "конвейера" документ и передавать его в обработку. Следующий модуль будет читать метаданные и в зависимости от них создавать "контейнер" в который будет класть содержание документа, промпт, кодовую строчку пайплайна для CDP модуля. CDP модуль получает контейнер. Из него берёт пайплайн и на его основе собирает последовательность действий. открытие вкладки, действия на странице, получение ответа, передача ответа в систему и дальнейшая обработка."

**Ограничения:**
- Чистые возможности Windows 10 без доп. софта и Python.
- Лимиты железа: 500 MB ОЗУ, маленький HDD.
- Однопоточность.

---

## 3. Уточнение технических деталей и браузера
**Запрос:**
"Брайзер ungoogled-chromium_129.0.6668.100-1.1_windows_x86. Формат входящих текстовые файлы .md. Авторизации не нужно. Я сам залогиню и авторизация будет в профиле. Однопоточность - да. Парсер мета данных да, но вся эта механика протом. просто чтобы учитывать это в закладываемых возможностях модулей. упрощать в ущерб производительности и потребления ресурсов готового решения - нельзя. Надо поработать над решением, будем работать."

**Логика пайплайнов:**
- Двухуровневая система: сначала идентификация (если тип неизвестен), затем специализированная обработка.
- Промпты берутся из "базы промптов".
- **Важно:** Передача данных через переменные в памяти, без промежуточной записи на диск. Запись только финального результата.
- Поддержка разных сайтов через универсальный CDP модуль ("касса деталей") или наборы пайплайнов.

## 5. Вопрос о межпроцессном взаимодействии и архитектуре
**Запрос:**
"Что будет для компьютера легче исполнять... Если мы запихнём в один скрипт пайплайны для нескольких сайтов... ИЛИ Для каждого провайдера свой отдельный скрипт...?"

**Решение:**
Разделение на Роутер (парсер/диспетчер) и отдельные модули-провайдеры для лучшей модульности и ремонтопригодности.

---

## 6. Вопрос о хранении переменных
**Запрос:**
"Переменные. Много ли они едят ресурсов системы? ... Чтобы скрипты получали данные из переменных ... ИЛИ Чтобы они читали их из INI файла?"

**Уточнение:**
Пользователь усомнился в существовании глобальных переменных между процессами в Windows.
"То есть для поддержания переменной в системе, требуется какой-то запущенный активный процесс... Как это в виндовс вообще устроено?"

**Вывод:**
Необходим единый процесс-менеджер (Роутер/Оркестратор), который держит данные в памяти и управляет потоком, избегая запуска изолированных процессов для каждой задачи.

---

## 7. Корректировка масштаба и разделение контуров
**Запрос:**
"Я тут спросил одного - доступны ли переменные между процессами... я хочу чтобы передача велась без лишней записи на диск."
*(После обсуждения Named Pipes и монолита)*
"Я сомневаюсь. Это только часть системы... А в системе будет более 100 агентов и бизнес процессы с их комбинациями будет не меньше... Получается всю эту логику тоже в скрипт?"

**Ключевое разделение:**
1.  **Контур 1 (Бизнес):** "Корпорация из 100+ сотрудников" (Агенты = промпты в Obsidian). Работают с файлами, не знают про "капот".
2.  **Контур 2 (Мета-логика):** Скриптовый движок (CDP транспорт + Оркестрация).
3.  **Провайдеры:** DeepSeek, Qwen, Kimi, GPT — это не агенты, а "движки" для выполнения запросов.
4.  **Интерфейс:** Веб-интерфейс для управления.

---

## 8. Детализация архитектуры и потока данных
**Запрос:**
"Теперь давай пошагово уточнять системную архитектуру. Всё лежит в БД Обсидиан в заметках. И агенты и бизнес процессы и файлы пользователя..."

**Логика работы:**
- Агенты — это промпты в `.md` файлах.
- Бизнес-логика берется из файлов (LangGraph или аналог).
- **Алгоритм:** Триггер -> Создание контейнера (файл + промпт) -> Конвейер -> CDP Модуль (читает маркировку провайдера) -> Ответ -> Обработчик (решает: записать или вернуть в конвейер).

---

## 9. Финальные правки к архитектуре
**Запрос:**
"Правки:
1. CDP не может получать от провайдера шагов, потому что мы работаем не через API, а через веб интерфейс. Логика селекторов, нажатий и всё остальное уже зашито в него заранее. Мозги только на этапе, когда веб ИИ принял запрос. До отправки и после — только скриптовая логика.
2. Финализатор не нужен. Оркестратор действует согласно логике бизнес-процесса. Он тупой (без ИИ), берет бизнес-процесс, переупаковывает контейнер для следующего агента, пока цепочка не закончится.
3. Вся передача информации от момента взятия файла до принятия работы происходит в оперативной памяти. Запись в Obsidian (на диск) только готового результата."

**Итог:**
Фиксация окончательной архитектуры с четким разделением ответственности: Оркестратор управляет графом процесса в памяти, CDP выполняет жестко заданные действия в браузере, данные не касаются диска до самого конца.
