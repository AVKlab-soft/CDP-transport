# Архитектура системы автоматической обработки файлов (EDC - Electronic Document Conveyor)

## 1. Общие принципы и ограничения

**Целевая платформа:** Windows 10 (x86)
**Ресурсы:** 500 МБ ОЗУ, ограниченное место на диске
**Зависимости:** Только встроенные средства Windows + ungoogled-chromium (портативный)
**Входные данные:** Текстовые файлы (.md)
**Режим работы:** Однопоточный, последовательная обработка

---

## 2. Компоненты системы

### 2.1. Диспетчер файлов (FileDispatcher.ps1)
**Назначение:** Мониторинг папки "Входящие", передача файлов в обработку.

**Функционал:**
- Опрос папки `.\inbox` каждые N секунд (настраиваемо,默认 2 сек)
- Блокировка файла на время обработки (переименование в `.processing`)
- Передача полного пути к файлу в модуль парсера
- Логирование событий в текстовый файл `.\logs\dispatcher.log`

**Техническая реализация:**
- PowerShell скрипт с использованием `System.IO.FileSystemWatcher` или цикл с `Start-Sleep`
- Минимальное потребление памяти (~10-15 МБ)

---

### 2.2. Парсер метаданных и менеджер контейнеров (MetaParser.ps1)
**Назначение:** Чтение .md файла, извлечение метаданных, формирование контейнера данных.

**Функционал:**
- Чтение содержимого .md файла в переменную (в оперативной памяти)
- Поиск YAML Front Matter (блок между `---`) или специальных тегов для метаданных
- Определение типа документа:
  - Если тип определен -> выбор соответствующего пайплайна
  - Если тип не определен -> назначение пайплайна "Идентификация"
- Формирование объекта-контейнера в памяти:
  ```powershell
  $container = @{
      SourceFile = "path/to/file.md"
      RawContent = "полный текст файла"
      Metadata = @{ Type = "unknown"; Tags = @() }
      PipelineName = "identification"
      PromptContext = ""
      TempData = @{} # Для промежуточных результатов
  }
  ```
- Передача контейнера в CDP модуль

**Хранение промежуточных данных:**
- Все промежуточные данные хранятся только в переменных PowerShell
- Запись на диск происходит только для финального результата и логов ошибок

---

### 2.3. База промптов и пайплайнов (Prompts & Pipelines)
**Назначение:** Хранение шаблонов промптов и логики пайплайнов.

**Структура хранения:**
- Папка `.\config\prompts\` - текстовые файлы с системными промптами
  - `identification.txt` - промпт для классификации документа
  - `invoice_processing.txt` - промпт для обработки счетов
  - `universal_extractor.txt` - универсальный экстрактор данных
- Папка `.\config\pipelines\` - JSON файлы с описанием шагов пайплайна
  - Каждый пайплайн описывает последовательность действий CDP

**Пример структуры пайплайна (JSON):**
```json
{
  "name": "identification",
  "steps": [
    {
      "action": "navigate",
      "url": "https://example-ai-service.com/chat",
      "waitFor": "networkidle"
    },
    {
      "action": "fill_selector",
      "selector": "textarea#prompt-input",
      "source": "prompt_file",
      "value": "identification.txt",
      "append_content": true
    },
    {
      "action": "click_selector",
      "selector": "button.send"
    },
    {
      "action": "wait_for_response",
      "timeout": 30000,
      "resultSelector": "div.response-content"
    },
    {
      "action": "parse_response",
      "parser": "json_extract",
      "targetField": "document_type"
    },
    {
      "action": "reroute",
      "condition": "document_type != 'unknown'",
      "newPipeline": "{document_type}_processing"
    }
  ]
}
```

### 2.4. CDP Модуль (CDPController.ps1 + HTA/JS)
**Назначение:** Управление браузером через Chrome DevTools Protocol, выполнение пайплайнов.

**Архитектура:**
1. **Запуск браузера:** PowerShell запускает ungoogled-chromium с флагами отладки:
   ```
   chromium.exe --remote-debugging-port=9222 --user-data-dir=".\browser_profile" --headless=new
   ```
2. **Связь с браузером:** 
   - PowerShell использует `System.Net.WebSockets.Client` (требуется .NET 4.5+) или HTTP polling для отправки CDP команд
   - Альтернатива: HTA приложение с JavaScript для WebSocket соединения (более надежно для старых систем)
3. **Исполнение пайплайна:**
   - Чтение JSON пайплайна
   - Последовательное выполнение шагов через CDP команды
   - Сохранение результатов каждого шага в `$container.TempData`

**Ключевые CDP команды:**
- `Page.navigate` - переход на URL
- `Runtime.evaluate` - выполнение JS в контексте страницы
- `DOM.querySelector` - поиск элементов
- `Input.dispatchMouseEvent` / `Input.dispatchKeyEvent` - эмуляция ввода
- `Network.getResponseForRequest` - получение ответов сети

**Обработка результатов:**
- Извлечение текста/JSON из страницы через JS инъекцию
- Парсинг ответа и обновление контейнера
- Принятие решения о следующем шаге (следующий пайплайн или завершение)

---

### 2.5. Менеджер результатов (ResultHandler.ps1)
**Назначение:** Сохранение финальных результатов, очистка памяти.

**Функционал:**
- Получение заполненного контейнера от CDP модуля
- Форматирование результата (текст, JSON, XML - настраиваемо)
- Запись в папку `.\outbox\` с именем `{original_name}_processed.md`
- Архивация исходного файла в `.\archive\`
- Очистка переменных и подготовка к следующему файлу

---

## 3. Поток данных (Data Flow)

```
[Файл .md] 
    ↓
[Папка inbox] 
    ↓ (FileDispatcher)
[MetaParser] → Чтение в память → Анализ метаданных → Выбор пайплайна
    ↓
[Контейнер в памяти] 
    ↓
[CDP Controller] → Запуск браузера → Выполнение шагов пайплайна → Получение ответа
    ↓ (обновление контейнера в памяти)
[Решение о маршруте] → (если нужна доп. обработка) → Другой пайплайн
    ↓ (если обработка завершена)
[ResultHandler] → Запись финала на диск → Архивация исходника
```

---

## 4. Стратегия работы с памятью

**Принципы:**
1. **Никаких временных файлов** для промежуточных данных
2. **Однопоточность** гарантирует, что только один контейнер находится в памяти
3. **Явная очистка:** После завершения обработки файла все переменные принудительно очищаются (`Remove-Variable`, `[GC]::Collect()`)
4. **Потоковая обработка больших ответов:** Если ответ от AI слишком большой, разбивать на чанки и обрабатывать частями

**Оценка потребления памяти:**
- PowerShell процесс: ~20-30 МБ
- ungoogled-chromium (headless): ~150-200 МБ (зависит от сложности страниц)
- Данные в памяти: ~5-10 МБ для типичных .md файлов
- **Итого:** ~200-250 МБ в пике (укладываемся в 500 МБ с запасом)

## 5. Конфигурация и расширяемость

**Папочная структура:**
```
EDC_System/
├── inbox/              # Входящие файлы
├── outbox/             # Обработанные файлы
├── archive/            # Архив исходников
├── logs/               # Логи работы
├── config/
│   ├── prompts/        # Тексты промптов
│   └── pipelines/      # JSON пайплайнов
├── browser_profile/    # Профиль браузера (куки, сессии)
├── scripts/
│   ├── FileDispatcher.ps1
│   ├── MetaParser.ps1
│   ├── CDPController.ps1
│   └── ResultHandler.ps1
└── MainRunner.ps1      # Точка входа
```

**Добавление нового пайплайна:**
1. Создать файл промпта в `.\config\prompts\`
2. Создать JSON пайплайна в `.\config\pipelines\` с описанием шагов
3. При необходимости добавить логику парсинга ответа в `CDPController.ps1`

**Поддержка разных сайтов:**
- Универсальность достигается через абстрактные шаги пайплайна (`navigate`, `fill_selector`, `click_selector`, `extract_by_selector`)
- Для каждого сайта создается свой набор пайплайнов с конкретными селекторами
- Возможна динамическая подгрузка селекторов из внешних конфигов

## 6. Риски и решения

| Риск | Решение |
|------|---------|
| Нестабильность CDP через PowerShell | Использовать HTA + JavaScript для WebSocket соединения с браузером |
| Превышение лимита памяти | Строгий контроль размера входящих файлов, потоковая обработка |
| Блокировка со стороны сайтов | Использование профиля с сохраненной сессией, рандомизация задержек |
| Ошибки парсинга метаданных | fallback на пайплайн идентификации, подробное логирование |
| Зависание браузера | Таймауты на каждый шаг, перезапуск браузера после N ошибок |
